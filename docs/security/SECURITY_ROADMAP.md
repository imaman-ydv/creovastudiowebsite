# Security roadmap

Audit snapshot: 2026-10-28. Status indicates the current repository state.

| Control | Status | Risk / affected files | Priority and mitigation | Complexity / compatibility | Required verification / trigger |
|---|---|---|---|---|---|
| Production configuration and secrets | **IMPLEMENT BEFORE PRODUCTION** | High if local Compose fallbacks are exposed; `docker-compose.yml`, `.env.example`, `backend/config/settings.py`. | Fail closed on production: `DEBUG=False`, required strong secret, unique DB credentials, exact hosts and HTTPS origins. Keep an explicit local-development path. | Low/medium. Must not make local setup opaque; deployment environment is unknown. | Django deploy check; verify startup rejects placeholders in production; inspect actual deployment env before exposure. |
| Public settings allowlist | **IMPLEMENT NOW** | Medium conditional data leak; `backend/content/views.py`, `SiteSetting` model/admin. | Return an explicit public key allowlist or model safe public/private settings with private-by-default behavior. | Low. May require mapping currently used frontend setting keys. | API tests prove allowed keys returned and private keys omitted; inspect consumers before narrowing output. |
| Contact abuse and request validation | **PARTIALLY IMPLEMENTED** | Medium spam/storage abuse; `backend/content/views.py`, Nginx config, static contact form. | JSON content type, 12 KB body cap, field/email validation, honeypot, and browser repeat-submit prevention are implemented. Before production, configure rate limiting using a deployment-appropriate key; avoid relying solely on IP throttling behind a proxy. | Medium. Keep successful `201` contract and legitimate accessibility/usability. | Tests for valid/invalid submissions, size limits, throttling, proxy IP handling, and repeated UI submissions. |
| CSRF policy for contact | **IMPROVE EXISTING** | Medium/low conditional browser request concern; contact view remains CSRF-exempt after the static contact form was wired. | Reassess same-origin CSRF protection for static HTML and cross-origin Flutter JSON; maintain strict CORS and document the threat model. | Medium. The current browser/Flutter callers may need different integration details; do not silently break form submission. | Browser integration test for legitimate submission and cross-origin/CSRF behavior. |
| Admin authentication | **IMPROVE EXISTING** | Brute-force/credential compromise; Django admin. | Review password policy, login throttling, MFA or identity-provider support, and access restrictions available in the real host. Add only controls compatible with the deployment. | Medium. Admin recovery and staff access need a supported path. | Test anonymous admin denial, staff authorization, login throttling, and recovery workflows. |
| TLS, cookies, headers | **IMPLEMENT BEFORE PRODUCTION** | Medium if served directly over HTTP; `docker/nginx.conf`, `backend/config/settings.py`, hosting edge. | Terminate HTTPS; enable secure session/CSRF cookies, HSTS after HTTPS validation, and suitable security headers. Add CSP via report-only first due third-party scripts. | Medium/high for CSP because existing external script/CDN behavior must remain intact. | Browser header/cookie inspection; CSP report review; regression checks for navigation/GSAP/Barba/analytics. |
| Third-party script supply chain | **IMPROVE EXISTING** | Medium browser-origin compromise; static HTML pages. | Inventory script owners and necessity, pin/version sources, add SRI where stable and supported, reduce unnecessary vendors; stage CSP. | Medium/high; visual effects and analytics can break. | Browser regression checks and CSP reports after each source change. |
| Dependency and container supply chain | **IMPLEMENT BEFORE PRODUCTION** | Medium; requirements, Dockerfiles, Flutter package lock. | Generate a reproducible Python lock with hashes; scan Python/Flutter dependencies and container images; update base-image tags/digests on a reviewed cadence; add secret scanning. | Medium; dependency updates can change compatibility and image size. | Scanner report, build reproducibility, vulnerability triage and resolved advisory evidence. |
| Container privilege and database roles | **IMPROVE EXISTING** | Operational compromise blast radius; backend/Dockerfiles and Compose DB account. | Run app processes as non-root where image/filesystem behavior allows; use a least-privilege runtime DB role separate from migrations/initialization when deployment warrants it. | Medium; file permissions, collectstatic, migrations and volume ownership need validation. | Container user inspection, migration/deploy check, database permission tests. |
| Database backup/data lifecycle | **IMPLEMENT BEFORE PRODUCTION** | Contact PII and content loss/exposure; PostgreSQL storage/deployment. | Define encrypted off-host backups, retention, access policy, restore procedure, inquiry retention/deletion, and incident response. | Medium; retention must match business/legal requirements. | Document and perform a restore drill before relying on production data. |
| API authorization/output | **IMPROVE EXISTING** | Public content exposure; `backend/content/views.py`. | Keep anonymous endpoints read-only and published-only; remove settings wildcard output; review future fields and link/image schemes. Admin remains server-authorized. | Low now; future editor UX may need explicit roles. | Anonymous/published-content tests, admin permission tests, output minimization review per endpoint. |
| Admin image uploads | **IMPROVE EXISTING** | Public image delivery and media storage; `Service.card_image`, `backend/config/settings.py`, Compose, Nginx. | Uploads are admin-only, image-decoded, restricted to JPG/PNG/WebP and 8 MB, and stored on a persistent volume. Keep the volume read-only in Nginx; include it in backup/restore. | Low/medium. Uploaded images are intentionally public and replacing an image may leave the prior file on disk. | Test staff-only upload, malformed image rejection, extension and size limits, public media URL, and backup restore. |
| Mobile integrity / anti-RE | **NOT APPLICABLE NOW** | No native Android/iOS app; Flutter target is Web. | Do not add mobile attestation or aggressive anti-debugging. Keep secrets and authorization out of client code. | N/A. Native targets would add platform signing/attestation complexity. | Reassess if Android/iOS release targets are introduced. |
| CI security pipeline | **IMPLEMENT BEFORE PRODUCTION RELEASE** | No CI workflow/scanner configuration found. | Add secret/dependency scanning, Django checks/tests, Flutter analysis/build, container scan, and release artifact controls to the existing/selected CI. | Medium; CI provider not identified. | Verify pipeline blocks committed secrets/critical findings and publishes reviewable artifacts. |

## Implementation order

1. Harden production settings and runtime secrets without changing local static-site behavior.
2. Restrict settings serialization and add API regression tests.
3. Add contact abuse controls and browser/Flutter form protection while preserving valid submission responses.
4. Confirm real production edge; add TLS/cookie/header policies and staged CSP.
5. Add dependency/container scanning, least privilege, backup/restore, and CI checks before first public release.

No code changes or production operations are authorized by this audit report itself. Do not deploy, rotate credentials, or mutate database records as part of these steps without explicit authorization.
